# Offline protocol 744: synthetic falsification experiment

**Status:** proposed synthetic protocol under test. This is not a production plan, not
application code, and not acceptance evidence. Passing it does not authorise implementation.
It does not reconstruct legacy history.

## 1. Purpose and frontier

The harness tries to *refute* one proposed protocol against known failure schedules.
Two kinds of test exist and are listed separately in `RESULTS.md`:

- **Paired schedules** (`protocol.test.cjs` F01–F13 except F01b and F10's candidate part)
  run against a **control** that reproduces the rejected behaviour and against the
  **candidate**.
- **Candidate-only checks** (F01b, the R02–R09 regressions in `correction.test.cjs`, P01,
  and the SDK and database fixtures) assert the candidate's boundary directly. Their RED
  was observed against the previous candidate, not against a control.

**Narrowed claims (correction pass):**

- Cache preservation starts when the cache v6 upgrade completes. Bytes an old writer
  replaces or clears while the upgrade is blocked are not recoverable; the protocol
  classifies what remains (`unverified` or `legacy-unresolved`) and never marks it lost.
- Snapshot re-send is shown only at the SDK wire boundary. Whether a server accepts a
  re-sent revision is not exercised; the rollback conflict in S3 is fixture-injected.
- The database fence relies on a synthetic `origin` flag and a fixture schema.

| Layer | What this experiment can show | What it cannot show |
|---|---|---|
| fake-indexeddb 6.2.5 + Node 22 WebCrypto | Real IDB transactions, aborts, version upgrades, blocked upgrades, two independent connections, real AES-GCM bytes | Real browser storage, multi-process tabs, eviction, PWA cache staleness |
| Installed Etebase 0.43.1 (transport intercepted, no network) | Exact wire fields for `transaction`/`batch`, snapshot cloning, baseline retention | Server behaviour, browser `Origin`, real network failure modes |
| Synthetic PostgreSQL / SQLite fixtures (CI only) | Engine locking, rollback and serialization of a synthetic fence + conditional write | The real Etebase server, real authentication, native or bridge HTTP behaviour |
| Not covered at all | — | Application integration, Android/bridge runtime, owner acceptance, production |

## 3. Proposed records (synthetic queue DB v2 + synthetic cache DB v6)

All replay authority lives in the queue DB. Every operation is a single IDB transaction
that checks the owner record inside that transaction.

| Store | Record | Notes |
|---|---|---|
| `meta['owner']` | `{fingerprint, lifecycleGen, envelopeId, session}` | Session is in the same record as the owner |
| `crypto['env']` | `{key: CryptoKey, envelopeId}` | Non-extractable key; cloned by IDB |
| `work` | `{id: tuple, collection, kind, workGen, seq, payloadId, status, attemptId, ackedAttempt}` | One live intent per tuple |
| `payload` | `{id, envelopeId, iv, ct}` | Ciphertext of the full intent, favourite included |
| `loss` | `{id: tuple#workGen, tuple, lossGen}` | Independent of `work`; never evicted |
| `attempt` | `{id, tuple, workGen, revUid, payloadId}` | Immutable; `add`, never `put` |
| `display` | `{id: tuple, seq, iv, ct}` | Encrypted display copy |
| `legacy` | `{id, kind, status, raw, cacheKey}` | Byte copy of legacy evidence |
| cache v6 `hold` | legacy primaries + cache key | Written in the cache `versionchange` transaction |

**Allowlisted plaintext:** tuple identifiers, kind, generation identifiers, sequence
numbers, status, revision UIDs. Item bodies and favourite values are only ever ciphertext.

## 4. Operations and linearization points

| Operation | Linearization point | Rule |
|---|---|---|
| `admit` | queue tx `[meta, work, payload, loss]` | Owner check (fingerprint + lifecycleGen + envelopeId); collection barrier check; move precedence; classify the old payload (absent or malformed → write a `loss` record) **before** replacing it; capacity on the post-state; `loss-capacity` rejects and leaves the old row untouched |
| `admitFavorite` | read, decrypt, then `admit` with expected `workGen` | Encrypted composition `{body, favorite}`; retry on generation change |
| `beginDispatch` | queue tx `[meta, work, attempt, payload]` | CAS on `(workGen, attemptId)`; materialised body sealed and registered **before** sending |
| `reconcile` | read attempts for the current generation | Any recorded `revUid` in server history → applied; else resend |
| `ack` | queue tx | Generation must still match; binds `ackedAttempt` |
| `publish` | queue tx `[meta, work, display, payload]` | Only the exact acked attempt; retire and display in one tx; memory updated only if not newer |
| `refreshPublish` | queue tx | Owner check; never overwrites a tuple with live work |
| `hydrate` | read | Display overlaid by durable work (deletes hide) |
| `replaceOwner` | queue tx | CAS on `lifecycleGen`; clears account data; writes owner, session, key together |
| `publishSession` | queue tx | Same-account: CAS on generation, keeps work |
| `beginCollectionDelete` / `collectionDelete` | queue tx | Barrier; classify each payload before retiring; refuse while a move is dispatched |
| `admitDeletes` | one queue tx | Admits up to remaining capacity; returns truthful `{admitted, rejected}` |
| `setFence` / `dispatchAllowed` | queue tx / read | Dispatch only when `active` and bound to the same server |
| `migrate` | cache v6 upgrade, then queue tx per legacy row | Upgrade blocked by any open old cache connection; legacy rows never auto-dispatch |

**Legacy classification (no invented provenance):**

| Legacy row | Held primary | Status |
|---|---|---|
| delete | any | `unverified-delete` (retained intent) |
| update | absent | `legacy-unresolved` (ambiguous: cleanup or loss) |
| update | malformed | `lost` + loss record |
| update | no key | `pending-locked` |
| update | fails authentication | `pending-ambiguous` |
| update | decrypts | `unverified` (may already be a server copy) |

Only `pending` is dispatchable; no legacy status is.
